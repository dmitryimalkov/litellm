# Перенос MCP-моста в dev-среду

Oct 4, 2026 · @Dimi

## Коротко

Скрипт `mcp_bridge.py` переписан так, чтобы перенос на другую ВМ и в dev-среду сводился к редактированию `.env`, без правки кода. Все адреса, ключи и имя модели вынесены в переменные окружения, в коде остались явные комментарии «ТОЧКА СОПРЯЖЕНИЯ» в местах, которые меняются между средами.

**Остаётся неизменным** между продом и dev: логика MCP-клиента (список инструментов, цикл function calling, системный промпт, лимит шагов), сам протокол связи с OpenMetadata через `/mcp`.

**Меняется между средами** — три группы параметров: адрес OpenMetadata MCP (если переезжает и каталог), и две точки сопряжения с LLM-инфраструктурой — см. ниже.

## Состав проекта

| Файл | Назначение |
| --- | --- |
| `mcp_bridge.py` | сам мост: MCP-клиент + цикл function calling к LLM-hub. Код не содержит жёстко зашитых адресов/ключей — всё через `os.environ` |
| `.env.example` | шаблон переменных окружения с теми же комментариями про точки сопряжения — копируется в `.env` и заполняется на месте |
| `requirements.txt` | `httpx`, `mcp`, `openai` — три зависимости для venv на новой ВМ |

Все три файла отправлены вам отдельным сообщением в чате.

## Две точки сопряжения с LLM-инфраструктурой

Обе отмечены в `mcp_bridge.py` и `.env.example` комментариями «>>> ТОЧКА СОПРЯЖЕНИЯ N <<<».

| # | Точка | Переменные | Сейчас (прод, cloud.ru) | В dev может стать другим |
| --- | --- | --- | --- | --- |
| 1 | **LLM-hub** — OpenAI-совместимый шлюз, который принимает запросы chat/completions и tools | `LLM_HUB_BASE_URL`, `LLM_HUB_API_KEY` | `http://127.0.0.1:4000/v1` — self-hosted LiteLLM на той же ВМ, мастер-ключ из `.env` | другой хост/порт LiteLLM в dev, другой ключ, или вообще другой OpenAI-совместимый шлюз |
| 2 | **Inference model** — имя (алиас) модели, заведённое в LLM-hub выше | `INFERENCE_MODEL` | `deepseek-v3.2` — алиас в LiteLLM, проксирующий на cloud.ru Foundation Models | своя ML-модель, заведённая в LiteLLM/шлюзе под своим алиасом |

**Важно:** модель в dev должна поддерживать OpenAI tool calling (function calling) — именно через него мост вызывает MCP-инструменты. Если своя модель это не умеет — мост в текущем виде работать не будет, потребуется либо добавить tool calling на стороне шлюза, либо переписать цикл вызова инструментов под другой формат (не входит в этот перенос).

Третья, независимая переменная часть — адрес самого каталога: `OPENMETADATA_MCP_URL`, `OPENMETADATA_TOKEN`. Она меняется, только если переезжает сам OpenMetadata, и никак не связана с двумя точками выше.

## Шаги развёртывания на новой ВМ

1. Скопировать на новую ВМ три файла: `mcp_bridge.py`, `.env.example`, `requirements.txt`.
2. Создать виртуальное окружение и поставить зависимости:

```bash
python3 -m venv mcp-bridge-venv
. mcp-bridge-venv/bin/activate
pip install -r requirements.txt
```

3. Скопировать `.env.example` в `.env` и заполнить реальными значениями: сначала `OPENMETADATA_MCP_URL`/`OPENMETADATA_TOKEN` (адрес и токен бота в том OpenMetadata, к которому подключаетесь), затем обе точки сопряжения — `LLM_HUB_BASE_URL`, `LLM_HUB_API_KEY`, `INFERENCE_MODEL` под dev-среду.
4. Экспортировать переменные и запустить:

```bash
export $(grep -v '^#' .env | xargs)
python mcp_bridge.py
```

5. При запуске скрипт печатает текущую конфигурацию (`[config] LLM-hub: ...`, `[config] Inference model: ...`) — это сразу показывает, к чему реально подключился мост, удобно сверить с ожидаемым.

## Как проверить, что перенос удался

- [ ] Строки `[config]` при запуске показывают именно dev-адреса LLM-hub и нужную модель, а не старые значения из cloud.ru
- [ ] Скрипт выводит список MCP-инструментов (значит, доступ до OpenMetadata есть)
- [ ] На пробный вопрос модель действительно вызывает инструменты (видно в логе `[MCP] Вызов инструмента: ...`) — если модель сразу отвечает текстом без вызовов, значит она не поддерживает tool calling — см. предыдущий раздел
- [ ] Ответ приходит за разумное число шагов (до `MCP_BRIDGE_MAX_STEPS`), без сообщения «Достигнут лимит шагов»

# Настройка MCP-моста OpenMetadata ↔ LiteLLM — шаги за 24.09.2026

Sep 24, 2026 · @Dimi

## Контекст и цель работы

Цель — построить «мост» между чат-клиентом, LiteLLM и встроенным MCP-сервером OpenMetadata: LLM (deepseek-v3.2 через LiteLLM) должна уметь вызывать инструменты OpenMetadata (поиск таблиц, метаданные, lineage и т.д.) через протокол MCP, чтобы отвечать на вопросы о данных платформы.

Архитектура:

```
Пользователь → CLI-скрипт (мост) → LiteLLM (127.0.0.1:4000, модель deepseek-v3.2)
                     ↕ (function calling)
              MCP-сессия → OpenMetadata /mcp (10.0.0.7:8585)
```

LiteLLM сам не умеет исполнять MCP-вызовы — поэтому мост является отдельным Python-процессом, который держит MCP-сессию с OpenMetadata и одновременно ведёт диалог с LiteLLM в режиме function calling.

## Шаг 1. Восстановление стека litellm-stack

Стек `litellm-stack` (`/opt/litellm-stack`, отдельный docker-compose проект) был остановлен за ночь. Поднял его командой `docker compose up -d` и проверил:

- `docker compose ps` — все 4 контейнера стека в статусе Up;
- `docker compose logs litellm --tail=20` — чистый старт без ошибок, в логах `Uvicorn running on http://0.0.0.0:4000`.

Регрессий не было — ранее исправленная проблема с `DATABASE_URL` (пароль Postgres содержала `/` и ломала парсинг URL) осталась решённой.

## Шаг 2. Создание бота OpenMetadata для моста

В OpenMetadata (раздел Bots в настройках) создан служебный бот `mcp-bridge-bot`:

- сгенерирован JWT-токен со сроком действия до 23 декабря 2026 (≈ 90 дней);
- опция **impersonation** (действовать от имени других пользователей через заголовок X-Impersonate-User) оставлена выключенной — мост действует как сам бот, а не от имени других.

Это — сервисный механизм аутентификации, отдельный от личных токенов пользователей — подходит именно для служебных интеграций вроде моста.

## Шаг 3. Токен в .env и проверка API

Токен бота добавлен в `/opt/litellm-stack/.env` как `OPENMETADATA_TOKEN`. Проверено прямым запросом к REST API OpenMetadata:

```bash
curl -H "Authorization: Bearer $OPENMETADATA_TOKEN" http://10.0.0.7:8585/api/v1/system/version
```

Ответ: `{"version":"2.0.2", ...}` — токен рабочий.

⚠️ В процессе проверки полный JWT-токен был вставлен в чат в открытом виде — стоит избегать этого впредь и при необходимости ротировать токен (критичность низкая — это не мастер-ключ, а скопированный токен бота, но хорошая практика — не палить секреты целиком в чат).

## Шаг 4. Loopback-порт для LiteLLM

Чтобы будущий Python-скрипт моста мог обращаться к LiteLLM напрямую (без TLS и без проблемы hairpin NAT), в `docker-compose.yml` сервиса `litellm` добавлена публикация порта только на loopback:

```yaml
image: ghcr.io/berriai/litellm:main-stable
ports:
  - "127.0.0.1:4000:4000"
```

Порт 4000 остаётся недоступным снаружи VM, но доступен локальным процессам на самой VM. Проверено:

```bash
curl -s http://127.0.0.1:4000/health/liveliness
# "I'm alive!"
```

## Шаг 5. Python-окружение для моста

- `python3 -m venv` сначала упал с `ensurepip is not available`; починено установкой пакета `python3.12-venv`:

  ```bash
  sudo apt update && sudo apt install -y python3.12-venv
  ```
- Создан виртуальный Python-окружение `/opt/litellm-stack/mcp-bridge-venv`.
- Активация через `source`/`.` не сработала (логин-шелл на VM — `sh`/dash, а не bash). Обошли: вызывали бинарники venv напрямую по относительному пути:

  ```bash
  ./mcp-bridge-venv/bin/pip install --upgrade pip
  ./mcp-bridge-venv/bin/pip install mcp openai
  ```
- Успешно установлены `mcp-2.2.0` и `openai-3.19.2` с зависимостями (httpx2, starlette, uvicorn, sse-starlette, pydantic, cryptography, pyjwt, jsonschema, anyio и др.).

## Шаг 6. Скрипт моста mcp\_bridge\_test.py

Написан CLI-скрипт `/opt/litellm-stack/mcp_bridge_test.py`, выполняющий:

1. Подключение к MCP-эндпоинту OpenMetadata по приватному адресу `http://10.0.0.7:8585/mcp` с токеном бота в заголовке Authorization.
2. Список MCP-инструментов (`session.list_tools()`) и конвертация их в формат OpenAI function calling.
3. Цикл диалога с LiteLLM (`http://127.0.0.1:4000/v1`, модель `deepseek-v3.2`): если модель запрашивает вызов инструмента — мост выполняет его через MCP-сессию и возвращает результат модели, повторяя до финального ответа (лимит 10 шагов).
4. Печать финального ответа модели, а также промежуточный вывод каждого вызова инструмента и его результата (для отладки).

Запуск: переменные окружения берутся из `.env` через `set -a; . ./.env; set +a`, сам скрипт запускается напрямую через `./mcp-bridge-venv/bin/python mcp_bridge_test.py`.

## Шаг 7. Отладка несовпадений API

Установленная версия `mcp` оказалась новее, чем ожидалось по памяти, поэтому пришлось итеративно подгонять скрипт под реальные сигнатуры, ориентируясь на тексты ошибок:

1. **Имя функции**: `streamablehttp_client` не существует — в этой версии она называется `streamable_http_client`. Исправлено импортом с алиасом.
2. **Заголовки авторизации**: у `streamable_http_client` нет параметра `headers` — токен передаётся через `http_client=httpx2.AsyncClient(headers={...})`.
3. **Формат возврата**: контекст-менеджер возвращает `TransportStreams` — это `tuple[ReadStream, WriteStream]` (пара), а не тройка `(read, write, _)`, как в более старых версиях SDK.
4. **Имя поля схемы**: у объекта `Tool` поле называется `input_schema` (snake\_case), а не `inputSchema`.
5. **Сходимость модели**: первый прогон упёрся в лимит шагов (6), модель перебирала варианты поиска, не дав финальный ответ. Поднял лимит до 10, добавил system-сообщение с просьбой останавливаться, как только данных достаточно, и вывод результата каждого вызова инструмента.

## Шаг 8. Успешный end-to-end тест

Запрос: «какие базы данных подключены в OpenMetadata?»

Модель самостоятельно выбрала цепочку инструментов (попытки `search_metadata` по `databaseService`, проверка `semantic_search` — отклонена, так как векторные эмбеддинги не включены на сервере, далее поиск по `table` и `database`, и `get_entity_details` для деталей подключений) и дала развёрнутый правильный ответ:

- **2 сервиса баз данных**: `demo-stand-postgres` (PostgreSQL) и `ClickHouseMeta-demo` (ClickHouse);
- **3 базы данных**: `salesdb`, `airflow` (в Postgres) и `audit` (в ClickHouse);
- **78 таблиц** суммарно, с разбивкой по сервисам;
- детали подключения (хосты `10.0.0.5`, фильтры баз, список ingestion-агентов: Metadata, Profiler, Usage, Lineage, AutoClassification).

Это подтверждает, что вся цепочка «клиент → мост → LiteLLM → MCP-инструменты → OpenMetadata» работает корректно end-to-end.

## Демо-сценарий для разработчиков

Цель демо — показать текущее состояние моста: стек жив, бот авторизован, а LLM через function calling реально дёргает инструменты OpenMetadata. Все команды выполняются на `litellm-stack` из `/opt/litellm-stack`.

### 1. Показать, что стек жив

```bash
cd /opt/litellm-stack
docker compose ps
curl -s http://127.0.0.1:4000/health/liveliness
```

Ожидаем: 4 контейнера в статусе Up, ответ `"I'm alive!"`.

### 2. Показать, что OpenMetadata доступен и бот авторизован

```bash
set -a; . ./.env; set +a
curl -s -H "Authorization: Bearer $OPENMETADATA_TOKEN" \
  http://10.0.0.7:8585/api/v1/system/version
```

Ожидаем: `{"version":"2.0.2", ...}`.

### 3. Запустить мост и показать список MCP-инструментов

```bash
./mcp-bridge-venv/bin/python mcp_bridge_test.py
```

При старте скрипт печатает `[MCP] Доступно инструментов: 15` — это момент, чтобы пояснить: это реальные инструменты OpenMetadata (поиск, lineage, качество данных и т.д.), которые модель теперь может вызывать сама.

### 4. Живой вопрос — обзорный

В ответ на `Вопрос:` ввести:

```
какие базы данных подключены в OpenMetadata?
```

В логах видно, как модель сама выбирает инструменты (`search_metadata`, `get_entity_details`), а в конце — связный ответ про 2 сервиса, 3 базы и 78 таблиц — это хорошая отправная точка для демо.

### 5. Живой вопрос — точечный (показать lineage / качество данных)

Запускаем скрипт ещё раз и задаём, например:

```

```

Здесь модель, скорее всего, пройдёт цепочку `search_metadata` (entityType=table) → `search_metadata` (entityType=testCase, по `originEntityFQN`) — хороший пример многошагового tool calling.

### 6. Что честно сказать об ограничениях (если спросят)

- Это пока CLI-прототип, не сервис с API — следующий шаг его обёрнуть в FastAPI-эндпоинт.
- `semantic_search` отключён на сервере (нет векторных эмбеддингов) — модель всё равно справляется через `search_metadata`.
- Сейчас используется master key LiteLLM — перед широким использованием нужен отдельный virtual key.
- Запись/изменение данных через инструменты `create_entity`/`patch_entity` в демо не показываем — только чтение/поиск.
